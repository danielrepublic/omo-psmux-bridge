§2  DESIGN OF THE FIX (what is in the helper now, and why it makes the trigger
    reachable)
STATUS: ACHIEVED

Read from the installed helper itself (30219 B / 722 lines). Two mechanisms were
added; both are needed, because neither alone closes the window.

a) PRE-FLIGHT RE-CHECK  (omo-opencode-port.ps1:662-672)
   The reservation is probed by Find-FreePort (a real bind that then closes) and
   is unguarded from that instant until the child binds it. The port is now
   re-probed with a real bind IMMEDIATELY BEFORE the exec. If it is gone, no
   child is launched at all: the loop spends a retry instead. This costs one
   bind and happens while no child exists, so it cannot collide with the child.
   On the last attempt there is no retry left, so it prints the exhaustion
   message and exits 1 rather than starting a doomed child.

b) BOUNDED LIVENESS WAIT  (Wait-ChildPortOutcome, omo-opencode-port.ps1:531-586)
   This is the part that makes the trigger reachable. After the exec the wrapper
   polls until one of three things is established, and returns it as a state:
     Exited  - the child is gone; its exit code is handed to the pre-existing
               exit-status rules, unchanged.
     Settled - the child owns the port (healthy), or nothing about the port
               proves otherwise. Either way this is NOT a steal, so the child is
               left alone and waited on exactly as the pre-fix wrapper did. A
               hang here is pre-existing behaviour, not a new one.
     Stolen  - the port is held by a process that is not our child.
   The loop body (:537-585), every iteration:
     1. $Proc.HasExited -> return Exited.
     2. Test-PortHasListener $Port  (:298-311) - READ-ONLY, via
        IPGlobalProperties.GetActiveTcpListeners(). It deliberately never binds:
        a bind probe is a real acquisition, and probing by bind while the child
        is racing for the same port would hand the child the very EADDRINUSE
        this code exists to prevent.
     3. If something is listening: Get-ListenerOwnerPid (:329-348) via
        Get-NetTCPConnection, then Test-PidInOurTree (:362-382), an ancestry walk
        over Win32_Process that returns 1 (ours) / 0 (definitively not ours) /
        -1 (cannot tell - the ancestry query failed).
             ours  = 1 -> PROVEN healthy: stop watching, WaitForExit(), Settled.
             ours  = 0 -> PROVEN starved: the child can never serve on the port
                          it was reserved, so return Stolen immediately - the
                          fact is already proven, there is nothing to wait out.
             -1    -> not evidence either way; fall through to the deadline.
        The -1 arm is load-bearing: without it a failed ancestry query would
        make our own healthy child look like a foreign thief and get it killed.
     4. Nobody listening is NOT evidence of a steal - a slow-starting or
        server-less opencode looks identical - so it keeps waiting.
     5. At $BindWaitMs, one definitive bind probe decides: bindable => Settled
        (not a steal, resume the old wait); not bindable => Stolen. At 10 s
        after exec the child has either bound long ago or never will, so there
        is no bind race left to lose.
   The caller (:684-697) then owns the single decision: on Stolen it writes the
   diagnostic, calls Stop-OwnedProcessTree on the handle it created (BFS over
   descendants, deepest-first, never a name-based sweep, so a bare user
   opencode.exe is unreachable), and `continue`s - which is the one permitted
   retry. On the final attempt it refuses to start instead.
   The retry itself is unchanged: Find-FreePort($FirstPort + 1), exactly once,
   guarded by `for ($attempt = 1; $attempt -le 2; $attempt++)` (:650).
   OPENCODE_PORT=0 is untouched: the digit test at :633 is still
   '^[0-9]+$', which accepts "0", and the $Reserved flag is only set on the
   Find-FreePort branch, so an explicit 0 still forwards verbatim with no
   reservation and no watching - deliberate parity with /home/daniel/.bashrc:29
   (`# Bypass: OPENCODE_PORT=0 opencode`).

§3  CHOOSING THE BOUNDED-LIVENESS-WAIT VALUE  (measured, with reasoning)
STATUS: ACHIEVED

VALUES IN USE, read from the installed helper (:94-95):
    $BindPollMs = 250        (poll interval for the liveness wait)
    $BindWaitMs = 10000      (the deadline - 10 s)

HOW 10 s WAS CHOSEN. The deadline is only ever reached when ownership cannot be
read at all (Get-ListenerOwnerPid returned -1 and Test-PidInOurTree returned
-1). When ownership CAN be read - the normal case - a steal is detected the
moment the foreign owner appears, typically within one $BindPollMs. So the
deadline exists for one purpose only: to stop the silent hang from being
unbounded. It therefore has to be comfortably longer than the worst time a
healthy child takes to bind its reserved port, and no longer than necessary.

BASIS - healthy child, process creation -> first listener on its reserved port,
n = 6, all on 7801, child creation to first listener (measured by the earlier
attempt, kept at %TEMP%\t23 and cited by the helper's own comment at :84-93):
    1790, 1793, 1809, 1834, 1799, 1756 ms   -> min 1756, max 1834, mean 1797
My own independent corroboration this pass, two data points:
    run 2 (healthy control): child --port 7801 first appeared at ~+600 ms and
      its listener was up at +2440 ms -> <= 1840 ms from creation.
    run 3 (retry child):      child --port 7802 first observed alive at
      +2461 ms, listener at +4641 ms -> <= 2180 ms from first sighting.
    (These are upper bounds: my polling saw the child late, never early.)

REASONING: 10 s is ~5.5x the worst healthy bind latency ever measured on this
host (1834 ms). Even if attribution is completely broken - Get-NetTCPConnection
erroring on every single poll - no healthy child is at risk, because the
deadline is only consulted after 10 s of a child that has not bound within 5x
the normal time. Symmetrically it caps the silent-hang window at 10 s instead of
forever, which was the actual defect.
NOT re-measured this pass: the n=6 distribution itself. It comes from the
earlier attempt's measurement (its %TEMP%\t23\lat.txt, reproduced in its
deploy log) and from the helper's comment; I corroborated the magnitude with
the two points above but did not repeat the 6-run series.

§11  RESIDUAL RISK
STATUS: ACHIEVED

1. THE DEADLINE ARM IS UNTESTED. Both passing runs were decided by the
   OWNERSHIP path (the message names the foreign pid), so the 10 s deadline's
   bind-probe branch was never exercised end to end. Its behaviour - bindable at
   10 s => Settled, not bindable => Stolen - is code reading plus the unit of
   logic in §2, nothing more.

2. THE -1 "CANNOT TELL" PATH IS UNTESTED AND IS THE ONE THAT CAN HANG AGAIN.
   If Get-NetTCPConnection keeps failing AND Test-PidInOurTree keeps failing,
   the wait falls through to the deadline; if a single bind probe at 10 s says
   the port is free, the wrapper returns Settled and goes back to waiting on the
   child - i.e. the original silent hang, now bounded at 10 s of looking but not
   eliminated. The mitigation for healthy children is real (killing needs
   positive evidence, so a healthy child is never killed), but the honest
   statement is that a pathological attribution failure degrades to the old
   behaviour rather than to a clean refusal.

3. Get-NetTCPConnection IS SLOW ON THIS HOST. It is a CIM cmdlet and inside the
   poll loop its cost dominates $BindPollMs=250. Measured effect: the
   steal -> retry latency was ~1.7 s in the clean run 3 and ~21 s in run 1,
   where my own concurrent CIM polling was loading the host. So $BindPollMs is
   not the effective interval; the real one is however long the ownership query
   takes. Raising $BindPollMs would not help; shortening the ownership query
   would. Not a correctness defect - every retry still landed correctly - but
   the user-visible stall after a genuine steal can be seconds, not
   milliseconds.

4. A >10 s HEALTHY START WOULD BE KILLED. The deadline's bind probe would see
   the port held by nobody and call it a steal. Measured healthy latency is
   1.76-1.83 s (n=6) so the margin is ~5.5x, but a pathologically slow start on
   a loaded host could cross it. There is no adaptive backoff.

5. ONE UNATTRIBUTED PROCESS, NOT REPRODUCIBLE. In run 1, 12 s after the retry
   settled, a third opencode.exe appeared: pid 3612, command line
   "...\opencode-ai\bin\opencode.exe" --port 7804. It exited on its own within
   seconds. It was NOT launched by the helper, and this is provable from the
   helper's own behaviour rather than argued: the helper emits "tmux detected"
   exactly once per instance, a retry line per retry, and its loop is capped at
   for($attempt = 1; $attempt -le 2) - so a third child would have required a
   second stderr line set that is not on disk. Both children the helper did
   launch (13528/7801 and 27172/7802) were observed directly. It did not
   reproduce in run 3, whose attribution walk found no stray. I could not
   attribute it: by the time I tried, the process was gone, and re-running to
   chase it was not worth the budget. UNEXPLAINED, and recorded as such.

6. THE MATRIX GAP (see §8) IS THE ONE THAT MATTERS MOST. Acceptance 1-3 are
   re-measured against the shipped binary; the other 38 contract cases are not.
   Before this todo is closed on anything stronger than "the C2 steal now
   recovers", the full matrix should be re-run against sha256 3033147366021E79
   ... against the 13925 B binary it was written for.

8. MEASUREMENT GOTCHAS ON THIS HOST, FOR WHOEVER RUNS THE NEXT PASS:
   * ProcessStartInfo + ReadToEndAsync returns EMPTY. Every comparison above
     came from Start-Process -RedirectStandardOutput/-Error to files.
   * With -PassThru, $p.ExitCode comes back NULL unless the handle is cached
     first ($null = $p.Handle). Without that, rc is "" and every exit-code
     assertion is vacuous.
   * Reading a redirect file while the writing tree is still alive throws
     IOException (the file is not opened FILE_SHARE_READ). All stderr content in
     §4 was read after teardown, except the tolerant timeline reader, which
     swallows the IOException.
   * `` `e `` in a PowerShell double-quoted string is NOT ESC on this host; a
     -replace on it silently eats every letter "e" in the displayed text while
     the bytes stay correct. Byte counts and sha256 above come from the files.
   * Nested-quote one-liners and stdin-piped PowerShell are broken over SSH
     here. Every run was one staged .ps1 fetched with one scp and executed with
     `powershell -NoProfile -ExecutionPolicy Bypass -File`, results fetched with
     one scp.
   * PowerShell console encoding here is BIG5; every result file was written
     with an explicit UTF8Encoding($false).
