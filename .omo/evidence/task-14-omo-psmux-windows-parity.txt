== A REAL DEFECT FOUND AND FIXED, IN THE REBUILT SHIM ==
Every translated case failed with classification=pass-through. Root cause: the shim did
not know psmux's own leading global flags. `-L <namespace>` must be the FIRST argument
(`psmux list-sessions -L ns` fails with "unknown option '-L'"), so with a namespace
argv[0] was `-L`, the grammar matched no verb, and ALL FIVE payload shapes degraded to
pass-through. The shim still forwarded the argv and still returned the backend's exit
code, so nothing failed loudly.

Proof, from the shim's own call log on the host, same binary path, same payload:
  before, no -L  : classification=pass-through     argv=[... ,"<the payload verbatim>"]
  before, with -L : classification=pass-through     verb=-L
  after,  no -L  : classification=placeholder-split argv=[... ,"<helper-invocation>"]
  after,  with -L : classification=placeholder-split verb=split-window
                        argv=["-L","omo_lexp_ns","split-window",...,"<helper-invocation>"]

Why this mattered more than an ordinary bug: this plan mandates a throwaway `-L`
namespace for todos 14, 15, 16, 18, 19 and 20. Under the plan's own verification method
the bridge would therefore have been measured ONLY in its pass-through mode, and a
reviewer would have concluded it works without ever exercising a single translation.
That is IS-8's "failure is loud" requirement, violated silently.

Fix, test-first: splitLeadingGlobals() in src/grammar.ts recognises the three value-taking
globals psmux 3.3.8 accepts before the verb (`-L`, `-S`, `-f`, each measured on the host),
TranslateOptions gained leadingGlobals so they are re-emitted in front of the rewritten
shape, and planInvocation() classifies the remainder and reports the real verb in the log.
13 new tests, written and seen failing before the fix existed.
bun test 214 pass / 0 fail (was 201). bun x tsc --noEmit exit 0.

== THE -h BRANDING DIVERGENCE, asserted rather than excluded ==
Measured: shim -h 16034 B, real tmux.exe -h 16022 B, psmux.exe -h 16034 B, 357 lines each.
The shim's help is BYTE-IDENTICAL to psmux.exe -h. 12 line indices differ from the real
one: 0, 3, 340-347, 349, 350.

The corpus's original rule -- "every `psmux` replaced by `tmux` must equal real" -- is
wrong twice over, and both errors were found by measurement rather than by reading:
  * the swap is ANCHORED at line start. psmux prints `psmux source-file ~/.psmux.conf`
    where real prints `tmux source-file ~/.psmux.conf`; the CONFIG PATH KEEPS ITS NAME.
  * the rule applies to the DIFFERING indices ONLY. Four lines are byte-identical on both
    sides and still say `psmux`: 152, 178, 197, 198. psmux substitutes `tmux` in
    COMMAND-VOCABULARY positions and keeps its own name in prose and in its own examples.
The contract now asserted is one-directional and is the one that actually holds: for every
line that differs, an anchored leading swap reconciles it, and the differing set is non-empty.

== METHOD NOTES, all measured on this host ==
* argv fidelity needs node spawnSync(exe, argvArray). Driving psmux through its .cmd
  launcher hands the line to cmd.exe, which consumed a `#{session_name}|#{pane_id}` format
  string at the `|`. A .cmd also cannot be CreateProcess'd directly: node returns status=null.
  The launcher is therefore only invoked with metacharacter-free argv, through cmd.exe, with
  the program path UNQUOTED; wrapping the line a second time makes cmd report that the quoted
  path is not a command.
* `-L <ns>` is only a global BEFORE the verb. Ordering is `-L ns VERB [opts]`.
* Both sides use the SAME namespace name, sequentially, torn down in between. Two DIFFERENT
  names are equally isolated but not comparable: `list-sessions` and every
  session-not-found message print the session name, so two names made two correct sides
  differ byte-for-byte.
* psmux prints its `created` stamp C-style (`Tue Oct  6 00:05:00 2026`), not ISO. Masking
  only an ISO pattern silently matched nothing and the comparison failed on a field that
  cannot match across two runs seeded seconds apart. Both forms are now masked, on 25 cases.
* A verb that opens or attaches to a pane needs a console. Over a non-interactive ssh there
  is none, so such a case is killed at 9 s and BOTH sides are recorded as console_blocked.
  That is an observation, not a pass: an empty stdout from a killed process is not evidence.
* The sweep must be launched with Win32_Process::Create. Start-Process and cmd /c children
  are killed when the ssh session's job object ends, which truncated the first run to nothing.
