2. WHAT IS TESTABLE WITHOUT WINDOWS, AND THE ONE THING THAT IS NOT
--------------------------------------------------------------------------------
Every environment touch point is an injectable seam with a production default:

  readEnv                 default process.env[name]
  readRegistryInstallDir  default: reg.exe, spawned directly (§2.1)
  readLocalAppData        default process.env["LOCALAPPDATA"]
  probePath               default statSync -> "file" | "directory" | "absent"
  currentExecutable       default process.execPath
  sameFile                default normalised+case-folded compare, then realpath
  spawn                   default node:child_process.spawn

So all four required resolution cases and every chain-guard case are asserted
IN-PROCESS on Linux, not deferred to a Windows host. The tests use
Windows-shaped fixtures (C:\Users\Someone\AppData\Local\psmux) so the
case-folding and separator handling under test is real Windows behaviour and not
a POSIX accident of the test host.

2.1  THE ONE GENUINELY WINDOWS-ONLY SEAM, AND HOW IT IS COVERED
`readRegistryInstallDir` defaults to spawning `reg.exe`:

  reg query HKCU\Software\psmux /v InstallDir

`reg.exe` is a real executable, so this is spawn(exe, argv) — no `cmd /c`, no
PowerShell wrapper, nothing that could re-interpret the value. It cannot be
exercised on Linux, so the part of it that contains any LOGIC is factored out
and exported as a pure function:

  parseRegQueryInstallDir(stdout, readEnv?) -> string | undefined
  expandWindowsEnvironmentReferences(value, readEnv) -> string

with 2 + 2 dedicated tests over real `reg query` output shapes (REG_SZ,
REG_EXPAND_SZ, value absent, error message, a neighbouring `InstallDirX` value
that must NOT be mistaken for `InstallDir`, an empty value that must yield
undefined rather than ""). Everything else about the seam is exercised by the
precedence tests, which inject the registry read.

4. THE CHAIN GUARD
--------------------------------------------------------------------------------
4.1  WHY IT IS CORRECT FOR BARE-NAME AND ABSOLUTE-PATH INVOCATION ALIKE
Two OmO call sites bypass any resolver and spawn the literal string "tmux"
(index.js:9072 findCommandPath("tmux"), plus the pane-command paths), so the shim
is routinely entered by BARE NAME. That needs no special case, and this is the
reason: the operating system resolves a bare name to a full path before argv[0]
exists, so process.execPath is an absolute path to the running image either way.
From inside the process, "bare name" and "absolute path" are indistinguishable.
The guard therefore compares the RESOLVED CANDIDATE against process.execPath and
needs no knowledge of how it was invoked.

What DOES need care is spelling, and this is asserted:
  - case-insensitivity, because Windows filesystems are: a lowercase-drive shim
    path still trips the guard on a mixed-case candidate.
  - separator equivalence: `\` vs `/`.
  - textual `..`: `<dir>\bin\..\psmux.exe` is the shim.
  - a symlink or Windows junction aliasing a candidate onto the running image:
    caught by the realpath half of sameFile, i.e. by consulting the real
    filesystem, not the strings. (Honest scope note: realpath resolves symlinks
    and junctions; it does NOT collapse NTFS hardlinks, and nothing here claims
    it does.)
  - an extra caller-supplied shim path is guarded identically.

4.2  THE RULE IS "SKIP THE SHIM, KEEP LOOKING", NOT "REFUSE AT THE FIRST MATCH"
A candidate that IS the shim is never executed, but resolution CONTINUES to the
next candidate. Exit 78 is returned only when nothing else is left to run. This
matters in the one realistic bad install — somebody dropped the shim into the
psmux directory next to an intact psmux.exe — where refusing outright would break
a setup that has a perfectly good backend sitting right there. Both branches are
tested:
  - "a self candidate is SKIPPED and resolution continues to a real backend"
  - "an exact self-match exits 78 with a message naming both paths"

4.3  CANDIDATE ORDER: psmux.exe, THEN tmux.exe
The shim is built as tmux.exe (todo 12), so a collision with tmux.exe is the
EXPECTED accident; trying psmux.exe first is what keeps such an install working.
tmux.exe is the fallback for a directory holding only the alias. Both emit the
same two-line -V at 3.3.8 (task-1 evidence field (e): identical stdout AND
identical exit code 0 for both), so the order costs nothing when both are present.

4.4  PROMPTNESS IS ASSERTED, NOT ASSUMED  (adversarial class: hung_commands)
The guard's whole purpose is that the failure mode is a HANG or infinite
recursion, so every guard assertion is also a boundedness assertion:
  - "the guard is PROMPT - a hang is the bug it prevents": asserts the guard
    returns with elapsed < 1000 ms.
  - "the resolver is a bounded synchronous read": asserts the result is not a
    Promise and that at most THREE probePath calls happen (the directory plus at
    most two candidate names) — i.e. no filesystem walk, no exec, no retry loop.
  - "forwarding is prompt": a -V round trip asserted < 10 s, test timeout 20 s.
  - "a real chain attempt through a compiled binary exits 78 and terminates":
    builds a REAL `bun build --compile` binary with `bun build --compile` inside
    the test, runs it with OMO_PSMUX_INSTALL_DIR pointing at the directory that
    holds nothing but that binary, and asserts exit 78 with the guard message on
    stderr. This is the end-to-end recursion proof and it found DEFECT 2 (§1).

4.5  THE MESSAGE
  omo-psmux-bridge: refusing to exec myself — the resolved backend <path> IS this
  executable (<shimPath>, matched by path). The psmux installation at <dir>
  (from <source>) contains no backend other than the shim. Move the bridge out of
  the psmux directory, or reinstall psmux, or set OMO_PSMUX_INSTALL_DIR to the
  real installation.

4.6  EXIT CODES
  78  chain guard only. sysexits EX_CONFIG — the shim's own configuration points
      it at itself. This is the plan's fixed code and the one an operator or a
      harness can key on.
  69  every other resolution failure. sysexits EX_UNAVAILABLE. Invented here, and
      documented as invented, because the plan fixes only 78.
   0  resolved.
Assertion: exitCodeFor(resolution) === resolution.exitCode for every
non-resolved kind, and exitCodeFor(resolved) === 0.

8. THE INTERFACE TODO 12 CONSUMES
--------------------------------------------------------------------------------
  import { resolveBackend, runBackend, exitCodeFor, describeResolution }
    from "./backend";

  const resolution = resolveBackend();          // synchronous, total, never throws
  const code = exitCodeFor(resolution);         // 0 | 78 | 69
  if (resolution.kind !== "resolved") {
    process.stderr.write(describeResolution(resolution) + "\n");
    process.exit(code);
  }
  const translated = translate(classifyArgv(argv), { psmuxPath: resolution.backendPath });
  const outcome = await runBackend(resolution, translated.argv);
  process.exit(outcome.exitCode);

Shapes todo 12 must know:
  - `resolution.backendPath` is the psmux path to feed as `TranslateOptions.psmuxPath`.
    It is the ONLY path in the result; everything else is trace-loggable by design.
  - `runBackend(backend, argv)` takes a ResolvedBackend, NOT a Resolution. That is
    deliberate: it is impossible to hand runBackend something that failed the guard.
    Resolve, check `kind === "resolved"`, narrow, then exec.
  - `runBackend` defaults to `stdio: "inherit"` (correct for an interactive tmux
    session). Pass `{ captureOutput: true }` for `-V`, which is the only probe that
    needs the bytes back.
  - `-V` wiring: `runBackend(resolved, ["-V"], { captureOutput: true })`, then
    write outcome.stdout UNMODIFIED and exit with outcome.exitCode. Do not print
    a banner, do not append a newline, do not forward stderr onto stdout. OmO's
    findVerifiedTmuxPath (index.js:9071-9091) treats a non-zero exit as "no tmux"
    and the gate at :8390-8394 then disables every tmux feature silently.
  - For interactive verbs, inherit stdin/stdout/stderr so psmux keeps its TTY.
    runBackend never sets `shell`, so a TTY-forwarded session is unaffected.
  - Do NOT let anything downstream re-derive the install directory. bridge.json is
    deliberately unread by this module; the registry is authoritative
    (CONTRACT.md 11.5) and a JSON file in a directory the shim may itself have
    written is one more route to pointing the shim at itself.

Nothing here is awkward to consume. One judgement call worth stating explicitly:
`exitCodeFor` returns 69 for install failures, a code the plan does not specify.
If todo 12 or todo 13 (bridge-doctor) would rather key on a different code for
"psmux is not installed", change INSTALL_FAILURE_EXIT_CODE in RESOLUTION_CONTRACT
— it is a single constant and nothing else depends on the number.
