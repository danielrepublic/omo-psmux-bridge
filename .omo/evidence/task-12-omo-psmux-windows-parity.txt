1. THE WIRING, AND HOW THE FOUR MODULES COMPOSE
================================================================================
Order of operations, and the reason for it:

    argv ──classifyArgv──▶ Classified ──translateArgv──▶ Translation
         ──resolveBackend─▶ ResolvedBackend ──runBackend──▶ exit code

  1. classifyArgv(argv)                        src/grammar.ts   (35 tests)
     Pure. Six outcomes. Total: never throws, never returns an error, and
     `pass-through` covers everything unrecognised — including empty argv and a
     bare verb, by its `argv.length < 2` rule.

  2. newCorrelationId(now(), nonce())          src/descriptor.ts (56 tests)
     Generated for EVERY invocation, pass-through included, so a log line for an
     unrecognised verb is still joinable with the helper's per-pane trace. It is
     then handed to the translator, which puts it in the helper invocation's
     `--correlation`; from there planDescriptor reads it back out.

  3. resolveBackend({readEnv, currentExecutable})   src/backend.ts (45 tests)
     Runs BEFORE the translation, not after, because TranslateOptions.psmuxPath
     is required and the Translation carries it back as a complete exec spec:
     `translation.psmuxPath` + `translation.argv` is everything needed to run,
     with nothing left to look up. Resolution failures are a RETURN VALUE, not a
     throw: an exception here would surface as a stack trace inside a pane and
     explain nothing, whereas Resolution.message says what was looked for.

  4. translateArgv(classified, {psmuxPath, helperPath, correlationId})
                                                        src/translate.ts (40 tests)
     Pure bookkeeping. Returns `kind: "passthrough"` byte-identically for
     unrecognised input, or `kind: "helper"` with the single-element PowerShell
     helper invocation, the `--` insertion for the two respawn forms, and the
     `-e` pairs addressed to numbered `OMO_PANE_ENV_<n>` slots.

  5. planDescriptor(translation, {bridgeRoot, profileDir})  src/descriptor.ts
     Pure. Returns undefined for a pass-through (no helper, no credential, no
     trace line) and undefined without a correlation id — which is why step 2
     generates one unconditionally.

  6. runBackend(resolution, translation.argv, {env})      src/backend.ts
     Direct spawn, `shell: false`, `windowsHide: true`, stdio inherited. No
     `cmd /c`, no PowerShell wrapper, no quoting layer of the shim's own. Output
     is returned verbatim.

  7. Two logs, then the exit code.

Nothing in src/cli.ts re-implements grammar, translation, backend resolution or
descriptor planning. It is the order, the seams, and the two logs.

`-V` GETS NO SPECIAL CASE, deliberately. It is a one-element argv, so
`classifyArgv` returns `pass-through` on the length rule alone and the
pass-through guarantee then forwards it byte-identically with
`rewritten === false` — asserted in test/cli.test.ts. A dedicated `-V` branch
would be a second place where `-V` could be handled and the two could disagree;
todo 14's parity sweep is what should decide whether the general rule is ever
wrong, not a branch.

WHY TWO, AND WHY 2b IS THE PROOF: the prior session's E2E enabled
OMO_PSMUX_BRIDGE_TRACE and it never fired, so it is treated as a bonus signal
only. Nothing reads it back, and BOTH writes are wrapped so a log that cannot be
written cannot change the exit code — asserted by a test that injects a
`writeLine` which throws and still gets exit 0. 2b exists because a provenance
claim has to be computable from the binary alone; hence no layout heuristic and
no environment override in its path.

DECISION FOR TODOS 14/15/20 (read this before looking for the file):
the call log is anchored on the EXECUTABLE'S OWN DIRECTORY, with no `bin`
special case. So a shim at `<root>\bin\tmux.exe` writes
`<root>\bin\state\shim-calls.jsonl`, and a shim at `dist\tmux.exe` writes
`dist\state\shim-calls.jsonl`. The directory is created by the shim on first
write, so no install step is load-bearing. Note this is NOT the same anchor as
the helper's per-pane trace file (`<root>\state\pane-<id>.jsonl`, named by the
helper from its own `<root>\runtime\` location): resolveDescriptorRoot() strips a
trailing `bin` for that one, because there the two MUST agree. The two anchors
differ deliberately and resolveDescriptorRoot() is where the difference lives.

3. WHAT IS DELIBERATELY ABSENT FROM BOTH LOGS
================================================================================
  * every `-e NAME=VALUE` VALUE, on every path, by POSITION and not by name:
    a bare `-e` (or `--environment`) plus the element after it collapse to
    `<redacted>`. `redactArgv` from src/descriptor.ts is applied on top as a
    second line of defence for a `NAME=VALUE` element that is not a pair at all.
    A credential called `FOO` is still a credential.
  * the payload body in ANY encoding. The helper invocation element is replaced
    wholesale by the literal `<helper-invocation>`, and the structure is recorded
    in the `helper` object instead. `--payload <base64url>` never appears; base64
    is not encryption, and src/translate.ts says so in as many words.
  * the attach URL, the session id and the working directory. Same reasoning as
    src/descriptor.ts's own trace line: a log file is exactly the sort of
    artefact that gets attached to a bug report.
  * each argv element is capped at 200 characters with the real length appended
    (`…(30000B)`), so a 30 KB argument cannot turn a log into a data store and
    the truncation is visible rather than silent.

BOUNDED, DELIBERATE, AND STATED: a PASS-THROUGH argv element is logged as given
(capped). If OmO sends an unrecognised payload-shaped element, that text appears
in the call log, because on the pass-through path it is simply an argument and
the attribution record is worthless if it hides what psmux actually received. The
"never the payload contents" rule is about what the shim EXTRACTS and re-emits on
a recognised shape, and there the base64 flag count in the file is 0 (section 6).

The translation itself forwards everything faithfully. The argv handed to
runBackend is `translation.argv`, unmodified; only the LOG projection is redacted.

8. DEFECTS FOUND BY THIS TASK
================================================================================
1. PRODUCT, FIXED. The default log writer double-stringified the record: both
   `appendJsonLine` and the `writeLine` seam ran `JSON.stringify`, so each line
   was a JSON STRING containing JSON — a file that parsed cleanly and was wrong.
   Caught by `first["v"]` being undefined while the raw bytes visibly contained
   `"v":1`. Fixed by giving the seam one job: `appendLine(target, line)` takes an
   already-serialised line, and exactly one place in the module decides how a
   record becomes bytes. Lesson worth keeping: a log format is only verified by
   PARSING it back and reading a field, never by reading the bytes.
2. HARNESS, FIXED. PowerShell's `Start-Process -ArgumentList` joins its array into
   one command-line string that the child re-parses, so the payload probe arrived
   as SEVEN argv elements and classified as pass-through. That is V-18's
   sibling defect on the argv axis: correct capture methodology is necessary but
   not sufficient — argv FIDELITY needs `spawnSync(exe, argvArray)`. Everything
   argv-fidelity-sensitive was moved to node; the PowerShell results that stand
   (`-V`, unknown verb) contain no spaces and are unaffected.
3. HARNESS, FIXED. `Count-Lines` returned -1 for a missing file, which inflated
   every before/after delta by one and made the trace hook look like it wrote 4
   lines for 3 invocations. It now returns 0. This is the misleading-success-
   output class in its purest form: the harness bug pointed straight at the
   product property under test.
4. PRODUCT, FIXED. `deps.shimPath` fed the call-log path but NOT the resolver's
   `currentExecutable`, so "which file am I" had two answers. Now one fact, passed
   to both. No production impact (both are `process.execPath`) but the seam was
   incoherent and it made the chain guard untestable off-Windows.
5. PRODUCT, FIXED. `resolveCallLogPath` used `node:path`'s `dirname`, which reads
   `\` as an ordinary character off-Windows and answers ".". The module's output
   is a Windows path by construction, so it now splits on the path's OWN flavour:
   the function returns the same Windows path whether asked on Linux or Windows.
   A path-derivation helper whose answer depends on the host is not a derivation.
